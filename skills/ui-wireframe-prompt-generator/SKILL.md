# UI Wireframe Prompt Generator

为 LoRA 或条件生图生成一段可直接使用的中文 UI 描述词。

## 必要上下文

- 目标 UX 线框图是结构依据。
- 用户可以为 `主题`、`背景`、`主视觉`、`UI皮肤`、`图标` 以及可选的不可变更/禁止项提供文字、图片或两者。
- 读取 [output-contract.md](references/output-contract.md) 了解最终输出格式。
- 当任一槽位缺失、含义不明确或与线框图冲突时，读取 [inference-boundaries.md](references/inference-boundaries.md)。
- 全量读取 [project-style-reference.md](references/project-style-reference.md) 获取稳定的项目风格 token。只有适用范围匹配时才使用条件规则。
- 当用户没有提供清晰的输入结构时，读取 [input-template.md](assets/input-template.md)。

## 交互策略

- 采用“最多一次追问”的两阶段流程。
- 首次处理请求时，检查 `主题`、`背景`、`主视觉`、`UI皮肤`、`图标` 五个槽位；任一槽位缺失、为空或含义不明确时，先统一向用户询问缺失项，不生成描述词。
- 追问必须一次性列出所有缺失槽位，并说明用户可以填写文字、提供图片、填写“自动推断”，或对主视觉填写“无独立主视觉”。
- 如果用户的下一次回复仍未补充某些槽位、回复为空、只回复“继续/直接生成”，或没有明确回答，视为放弃补充；不得再次追问，立即按现有流程对剩余槽位进行推断并生成最终描述词。
- 用户补充部分槽位后，未补充的槽位同样不再追问，直接按现有流程推断。
- 追问阶段可以输出简短的结构化问题；生成阶段仍必须遵守下方输出合同，只输出最终单段描述词。

## 工作流程

0. 先执行“交互策略”的槽位检查；若触发追问，等待用户下一次回复后再继续，不在同一轮生成描述词。
1. 检查线框图，并在内部记录画幅方向、区域、可读文字、组件数量、位置、层级、占位框、选中/锁定/禁用状态、角标、红点和遮挡关系。将这些内容视为不可变更项。
2. 将用户提供的每项文字/图片参考提取到对应槽位。参考图只提供视觉属性，不提供其无关的布局、文案、数量、角色、商品或页面结构。
3. 按以下证据优先级处理：线框结构和文字；用户明确约束；槽位对应的参考图；[project-style-reference.md](references/project-style-reference.md) 中适用的已审核项目风格 token；通用游戏 UI 语义。不要在运行时读取或检索原始训练描述词。
4. 对图标单独执行选择顺序：先采用用户提供的图标约束或图标参考；再从 `project-style-reference.md` 中选择与组件语义相符的既有图标类别、容器或状态规则；仅在没有可用的既有图标类别时，依据线框中的占位框、相邻文字和组件位置作最小范围的类别推断。图标内容不得脱离页面文字和组件功能自由联想。
5. 根据线框文字、组件语义和项目风格补全缺失的背景、主视觉和皮肤细节；图标按上述专用顺序补全。证据较弱时降低描述具体程度。不要编造专有名称、角色身份、故事、品质或机制。
6. 按空间顺序描述成品画面：背景、主视觉、UI皮肤、图标。每个新增对象都要包含相对位置和所属区域。将线框图中的全部文字、数字、间距、组件数量、排列和状态转述为目标 UI 的确定外观。
7. 对照 [qa-checklist.md](references/qa-checklist.md) 在内部自检，必要时修改，然后只输出最终单段描述词。

## 硬性边界

- 生成阶段不输出分析、备选方案、置信度、Markdown 或单独的负面提示词；仅在首次槽位缺失时允许输出一次简短追问。
- 不新增、删除、移动、缩放、合并、重新排序或重新设计线框组件。
- 不复制任何参考内容中的无关布局、文案、数量、角色、商品或页面结构。
- 不使用“精美、震撼、高清、高级感、炫酷”等空泛评价。
- 最终描述词只描述期望生成的成品 UI，不得出现“线框图、参考图、推断、优先、依据、保留、保持、占位、自动推断”等来源、过程或不确定性措辞。
